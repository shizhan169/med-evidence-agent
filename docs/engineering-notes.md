# 工程问题记录

MedEvidence Agent 从 0 到 1 过程中遇到的真实工程问题。每个问题按「开始的效果 → 遇到的问题 → 原因 → 怎么改的 → 提效」记录，面试时可直接讲。

---

## 1. numpy 2.x 与 chromadb 0.5.0 版本冲突（2026-11-24）

- **开始的效果**：按 requirements 装完依赖，跑 ingest 直接报错，Chroma 向量库起不来，一步都走不下去。
- **遇到的问题**：`import chromadb` 报错，提示 numpy 不兼容。
- **原因**：chromadb 0.5.0 不支持 numpy 2.x，而环境里默认装的是 numpy 2.4.6。
- **怎么改的**：把 numpy 钉死在 `<2`（降回 1.x），写进 requirements。
- **提效**：从完全跑不起来 → 入库和检索全部正常。教训：新库的大版本升级要先看下游依赖的兼容范围，不能默认最新版能用。

## 2. HuggingFace 镜像连不上，embedding 模型下不下来（2026-11-24）

- **开始的效果**：ingest 跑到加载 embedding 模型那一步卡住报错，bge-small-zh-v1.5 下载失败。
- **遇到的问题**：Python 的 huggingface_hub 连不上 hf-mirror.com；但同台机器上 `curl.exe` 能正常访问该镜像，huggingface.co 域名解析直接失败。
- **原因**：用户本地网络 / VPN 对 Python 的 HTTPS 请求有限制（curl 能通、Python 不通，说明不是镜像本身挂了，是请求链路的问题）。
- **怎么改的**：改用 ModelScope 把模型下载到本地 `./models/bge-small-zh-v1.5`，`.env` 里 `EMBED_MODEL` 指向本地路径，不再联网下载。
- **提效**：从模型加载失败 → 本地加载成功，ingest 顺利跑通。教训：关键模型放本地，不依赖每次运行时的网络；PowerShell 里 `curl` 是 Invoke-WebRequest 的别名，测连通性要用 `curl.exe`。

## 3. pypdf 提不出纯图表页文字，片段数对不上（2026-11-24）

- **开始的效果**：早期用 pdftotext 做切分测试，5 篇论文 836 个片段；实际 ingest 入库只有 509 个片段，差了 327 个。
- **遇到的问题**：两边数字对不上，一度以为是 ingest 漏了内容。
- **原因**：不是漏了，是口径不同。测试用 pdftotext，ingest 用 pypdf；pypdf 对纯图表页提不出文字，那些页被跳过（ingest 里还跳过 <50 字的过短片段）。
- **怎么改的**：没改代码，做了口径对齐：对外（简历、汇报）统一用 ingest 的实际入库数 509，不用测试数 836。
- **提效**：不是性能问题，是避免了简历写错数字。教训：同一个指标，测试工具和生产工具不同，结果就不能直接混用。

## 4. 引用列表重复（2026-11-24，commit 16bb393）

- **开始的效果**：第一次带引用问答跑通后，引用列表里同一篇论文同一页出现多次，又长又乱。
- **遇到的问题**：多个检索片段来自同一篇论文的同一页，引用是按片段逐条列的。
- **原因**：引用去重缺失。
- **怎么改的**：加 `_dedupe_citations`，按 (source, page) 去重后再输出引用列表。
- **提效**：引用列表变干净，一篇论文一页只出现一次，演示时看着专业。

## 5. Chroma telemetry 报错、pypdf ARC4 警告（2026-11-24）

- **开始的效果**：每次运行 ingest / 问答，终端刷一堆报错和警告，看着像出问题了。
- **遇到的问题**：Chroma 报 `Failed to send telemetry event ... capture() takes 1 positional argument but 3 were given`；pypdf 报 ARC4 弃用警告。
- **原因**：Chroma 0.5.0 的 telemetry 回调签名不匹配；cryptography 库弃用了 ARC4 算法。都是库内部问题，不影响功能。
- **怎么改的**：确认是无害噪音后没修，只在文档里记下来；升级 Chroma 到 0.6+ 或换 FAISS 留到第 2 周评估，不阻塞 MVP。
- **提效**：0（功能本来就没受影响），但省了折腾升级的时间。教训：先分清“报错”和“警告”，不是所有红字都要修。

## 6. 文献下载被机器人验证 / 403 拦截（2026-11-24）

- **开始的效果**：30 篇目标文献，后台只下到 17 篇，13 篇下不下来。
- **遇到的问题**：PMC 全文下载被 proof-of-work 机器人验证拦截（11 篇），Wiley / Elsevier / JAMA / Neurology / J Neurosci 出版社站直接返回 403（9 篇），medRxiv 返回 403（1 篇）。
- **原因**：出版社的反爬策略，没登录任何账号、没付费的情况下拿不到全文。
- **怎么改的**：用户用学校权限补了 9 篇，库到 26 篇；剩下 4 篇（Wolfers 2018、Bayer 2022、Subramaniapillai 2026、Macleod 2025 仅摘要）暂缓，26 篇已够用。
- **提效**：17 篇 → 26 篇，片段 509 → 3195（6 倍多）。教训：外部资源拿不到时，先用手头能拿到的跑通全链路，别卡在“凑满数字”上。

## 7. 评测：检索召回不足，可回答题大面积答不出（2026-11-25，已修复，待重跑验证）

- **开始的效果**：20 题评测，终端显示“已答 12、拒答 8”，引用准确率 9.1%（1/11），应拒答答对 4/5，编造 1 次。
- **遇到的问题**：看 eval/results.json 后发现，12 道“已答”里有 6 道其实是“拒答 + 解释”（Q01、Q04、Q05、Q08、Q09、Q10），模型实质上没答出来；真正答出来的只有 5 道（Q02、Q15 完整，Q03、Q11、Q14 部分）。根本原因在检索，不在回答：10/15 道可回答题，预期来源的片段根本没进 top-5 检索结果。例如 Q01 要的是 Bethlehem p.1（摘要，含 123,984 次扫描、101,457 人），检索返回的却是 Ge p.3、Coupé p.1 等别的片段；Q07 要 Fujita p.1/p.4，返回的是 Seidel、Kia、Bethlehem、Hedman 的片段。模型没拿到依据就老实拒答了（这是对的），但系统因此答不出本该答出的题。
- **原因**：问题是中文，文献是英文，embedding 模型是中文小模型 bge-small-zh-v1.5，跨语言向量检索弱；top_k=5 在 3195 个片段、26 篇文献里太小，关键片段排不进前 5。
- **怎么改的**（commit 9602354）：
  1. 混合检索：向量检索 top_k 从 5 提到 10，再加关键词兜底——从问题里抽英文词和数字 token（论文名、术语、年份、数字，如 Bethlehem、MFPR、CentileBrain、123,984），按 token 命中数给全库片段打分，补 5 个向量漏掉的片段。关键词与语言无关，正好补上跨语言检索的短板。
  2. Prompt 加第 4 条规则：每个引用单独写一个括号，不许用分号合并（Q06、Q12 曾因合并引用被核查器拒答）。
  3. 核查器正则改成能解析合并引用的形式（匹配所有“X.pdf p.N”，“来源：”前缀不计入文件名），双保险。
- **提效（第一轮修复后）**：第二轮评测（2026-11-25 08:34）终端显示已答 8、拒答 12，引用准确率 14.3%（1/7）——但看 results.json 发现实质答出的还是 5 道（Q02、Q03、Q11、Q14、Q15），Q01、Q08、R03 是带分号 / 冒号的拒答变体，又被误算成已答；R03 的“编造”仍是误判（实质是拒答）。也就是说第一轮修复基本没起效。
- **第二轮发现的新 bug（我自己的）**：关键词兜底等于没跑。代码是向量先拿满 10 个，再追加 5 个关键词片段，最后 `[:top_k]` 把关键词的全截掉了。对照两轮检索记录能证实：Q05 第二轮多出的 5 个片段全是向量第 6–10 名，没有一个是关键词补进来的。
- **第二轮修复**（commit ee90c81）：
  1. 向量和关键词各占一半名额（各 5 个），关键词的片段一定能进最终结果；
  2. 关键词打分加文件名加权（论文名就在文件名里，加权后该论文的片段排前面，避免同分被入库顺序挤掉）；
  3. embedding 模型换成多语言 bge-m3（1024 维），中文问题查英文文献从语义上解决——第一轮“先用关键词验证”的策略已证明不够，数字说了话才换；
  4. 评测拒答判定去掉句号要求，匹配“根据现有文献无法回答”前缀，分号 / 冒号变体不再误判。
- **提效**：待重跑评测后填（需先下载 bge-m3、删 data/chroma、重新入库）。本地单元测试已验证：关键词片段能进结果，Bethlehem p.1 靠文件名加权排在关键词首位；三种拒答变体都能正确判定。
- **扩展性质疑与再改（2026-11-25 08:39）**：用户指出关键词补丁太针对性——库扩到 100/1000 篇、或给别人用原始文件名时就没用了。是对的，三处硬伤：① 每次查询全库取一遍再打分，3195 个片段还行，12 万个片段就慢了；② 文件名加权依赖我方“年份-作者-标题”的命名，别人用原始文件名（如 1-s2.0-...main.pdf）就失效；③ 通用 token（brain、2022、mri）一多就同分，靠入库顺序决胜负。已改成标准 BM25（commit 58a9d37）：词频 + 逆文档频率加权，索引只建一次并缓存、库变了才重建，1000 篇也能用；文件名 token 也放进索引，但机制本身不依赖命名格式，原始文件名只是匹配不上、不会出错；rank-bm25 没装时退回 token 计数兜底。本地单元测试：Q01 的关键词第一名是 Bethlehem p.1，Q12 的关键词第一名是 Ge p.1（MFPR 那页）。
- **提效（第三轮评测，2026-11-25 09:15，BM25 + bge-m3 重跑，26 篇 / 3195 片段）**：20 题，终端显示已答 11、拒答 9；可回答题答出 11/15（第一轮 5/15，第二轮 5/15）；引用准确率 100%（11/11，第一轮 9.1%，第二轮 14.3%）；应拒答答对 5/5，编造 0 次。逐题核对 eval/results.json：完全答对 8 道（Q01、Q03、Q07、Q10、Q12、Q13、Q14、Q15）；部分答对 3 道（Q02 缺 95% 置信区间和峰后下降、Q04 只给了“显著低估”的定性结论、没给 44%/37%/35%/26% 四个数字、Q08 没给出全脑体积的 0.4%/年、给了皮层和海马的数）；仍答不出的 4 道里，Q05（要 Di Biase p.2）和 Q11（要 Ge p.1）是检索漏召回，Q06（Di Biase p.3 已召回）和 Q09（Fujita p.8 已召回）是数字在图里、pypdf 提不出文字。结论：检索问题基本解决，下一瓶颈是图表解析（第 2 周计划里的图表图注解析）。Q11、R02、R05 的“核查通过：False”是核查器设计：裸拒答没有引用可核查，verified 恒为 False，不是答案错了，评测的“编造 0 次”和“应拒答 5/5”不受影响。

## 8. 评测：R04“编造 1 次”是评测脚本的误判（2026-11-25，已修复）

- **开始的效果**：R04（阿尔茨海默病患者海马体积年萎缩率）被算成 1 次编造。
- **遇到的问题**：看 eval/results.json 发现，R04 的回答实际是“根据现有文献无法回答。提供的片段未包含阿尔茨海默病患者海马体积年萎缩率的数据；……”——实质是拒答，只是后面多了一句解释。
- **原因**：评测脚本用整句相等判拒答（`answer == "根据现有文献无法回答。"`），带解释的拒答被误判成“已回答”，编造次数虚高。同一个 bug 也让“已答 12”虚高（6 道实质拒答被算成已答）。
- **怎么改的**：拒答判定改成开头匹配（`startswith`）。改完后编造次数应为 0。
- **提效**：指标从“编造 1 次”修正为 0 次；“已答”从 12 修正为实质答出的 5 道。教训：评测脚本的判定规则本身也要验证，指标异常时先核对评测逻辑，再怀疑系统。
- **第三轮验证（2026-11-25）**：R04 这次是带解释的拒答，编造 0 次，误判已彻底消除。另发现一处同类显示问题：Q11、R02、R05 的“核查通过：False”也是核查器设计——裸拒答（`draft == REFUSAL`）或答案里没有任何引用时，核查器直接返回 verified=False，因为没有引用可核查。评测脚本的“编造 0 次”和“应拒答 5/5”不受影响，但终端显示容易误读。暂未改代码，记下来以后修。

## 9. 评测：Q04/Q06/Q08/Q09 答不出，数字以为在图里、其实在正文（2026-11-25）

- **开始的效果**：第三轮评测（2026-11-25）答出 11/15，引用准确率 100%；剩下 4 道里 Q05、Q11 是检索漏召回，Q06、Q09 的目标片段已经召回、但模型说数字不在片段里，Q04、Q08 只答对一半。当时以为数字只在图里、pypdf 提不出来，下一瓶颈是图表解析。
- **遇到的问题**：调查发现不是这么回事。用 pypdf、PyMuPDF（fitz）、pdfplumber 三个工具分别提 Fujita 2023 p.8 和 Di Biase 2023 p.3、p.2 的文字：Q06 要的 18%/7%/4%/2% 和 Q04 要的 44%/37%/35%/26% 三个工具都能提到；Q09 要的脑室 1.8% 在 Fujita p.4、p.5 的正文里就有（"an overall annual increase in ventricle volume of 1.8%"），Q08 要的全脑 0.4% 也在 p.4 正文（"an annual decrease of –0.4% in whole-brain volume"）。只有 Fujita p.8 图里的 1.8% 是画出来的中位线位置、从来没印成文字——OCR 也提不出来，不是 OCR 能解决的问题。
- **原因**：真正的毛病在切分，不在提文字。原来是固定 800 字网格切：① 经常把一句话从中间切断（"pre- dictions" 这种半个词）；② 结论句和数字句被切到两个片段里，检索只拿到结论片段、看不到数字。Q06 的数字句和结论句明明在同一个 800 字窗里（@1400），但检索返回的却是只有结论、没有数字的 @700 片段；Q09 的 p.4 数字句根本没进前 10。图注里也没有这些数字（Fujita p.8 的图注只是图题），所以“图注单独成片段”也帮不上忙；换 fitz 提文字也没有多提回目标数字。
- **怎么改的**：`app/ingest.py` 改成按句子切分：先把行尾连字符断词接回去、换行换成空格，再按句号分句（缩写 Fig./e.g./i.e. 不切），句子是最小单位、不拆句子，打包到 800 字；超长句子才按词切；相邻片段按整句重叠约 300 字（重叠 0/100/200/300 都实测过，300 时 BM25 前 5 命中 6/11、和旧切分持平，200 时掉到 4/11）。没换解析器（pypdf 保留），没加新依赖，没做 OCR；新增 `eval/check_retrieval.py` 做检索级验证（不需要 LLM/Chroma/embedding 模型）。
- **提效**：检索级验证（`eval/check_retrieval.py`，退出码 0）：4 道目标题的数字和上下文现在都在同一个片段里，Q04/Q06/Q08/Q09 同框片段从各 1 个变成各 2 个；15 道题的预期答案探针一个没丢；BM25 前 5 命中 6/11，和旧切分持平（旧 6/11）；干净开头片段从 25% 提到 94%，行尾连字符断词残留从 2100 处清到 0 处；片段总数 3195 → 4220。向量检索的实际提分要等用户本地重跑 `python eval/run_eval.py` 看数字。

## 10. 多轮对话：追问“那白质呢？”接不上上文（2026-11-25）

- **开始的效果**：单轮问答能跑，但追问接不上上文。先问“总皮层灰质体积（GMV）在几岁达到峰值？”再问“那白质呢？”，系统只看“那白质呢”几个字检索，答不对。
- **遇到的问题**：两个断点：① 检索只看当前问题，追问里的“那”“白质”没有指向，检索不到白质体积的片段；② 回答员的 prompt 里没有历史，模型不知道“白质”是接着上文的“总白质体积（WMV）”说的。
- **原因**：LangGraph 的 State 里只有 query/chunks/draft/final/verified，没有对话历史；FastAPI 的 POST /ask 只收 query；Streamlit 问完就丢，没有把历史传回去。
- **怎么改的**：① `app/agent.py`：State 加 `history`（最近 6 轮，一轮一问一答）和 `retrieval_query`；`_normalize_history` 清洗历史（只要 user/assistant、去空、留最近 6 轮、总字数超 4000 就从最早一轮开始丢）；`_build_retrieval_query`：问题里有指代词（那/它/这个/那个/呢）且有历史时，把上一轮用户问题拼在前面再检索，普通问题原样返回；`run(query, history=None)`，不传 history 就是原来的单轮行为。② `app/rag.py`：`build_prompt` 加 `history` 参数，历史只用来理解指代，并加规则“引用只能来自本次提供的文献片段，不要引用历史里的页码”（历史里的引用可能不在本次检索结果里，核查员会判错）。③ `app/main.py`：`POST /ask` 接受可选的 `history` 字段。④ `app/streamlit_app.py`：历史存 `st.session_state`，每轮问答后追加，带“清空对话”按钮。⑤ 新增 `tests/test_multiturn.py`（8 个测试，不需要 LLM/Chroma/联网）。
- **提效**：测试 8/8 通过：历史截断（10 轮→留 6 轮）、脏数据清洗、字数上限、追问改写（“那白质呢？”拼上上文）、单轮行为不变、prompt 含历史、假 LLM + 假检索端到端（追问答对、核查通过）；FastAPI 实测：带 history 和不带 history 的 POST /ask 都返回 200，向后兼容。真的多轮问答效果（追问答对率）要等用户本地跑完整评测/手动试。

## 11. 入库崩了：DuplicateIDError，4220 个片段一个都没写进去，评测 0/20（2026-11-25，已修复）

- **开始的效果**：按句子切分 + 多轮对话改完后，用户本地重跑评测，20 道题全拒答，引用准确率 0.0%（0/0），只用了 27.9 秒。
- **遇到的问题**：看 results.json，20 道题的引用列表全是空的——检索一个片段都没返回，LLM 一次都没调。用户重跑入库才看到真正的报错：`chromadb.errors.DuplicateIDError: Expected IDs to be unique, found 85 duplicated IDs`，入库在 `collection.upsert` 那一步直接崩了，4220 个片段一个都没写进去，库是空的。
- **原因**：入库 ID 是 `{论文名}-{页码}-{chunk_start}`，而按句子切分有个新情况：相邻片段会重叠——上一个片段如果只有一个句子（比如一页的第一个句子特别长、700 字，自己占了一个片段），下一个片段会从同一句开头，两个片段的 `chunk_start` 完全相同，ID 就撞了。旧的网格切分是按固定步长 700 推进，`chunk_start` 永远是 0、700、1400……不会撞；新切分一换就撞了 85 个。更糟的是 `add_chunks` 是一次性 upsert 4220 个，校验失败就整批作废，一个都不写；而且 `retrieve()` 在库为空时静默返回空列表、不报错，评测看着“一切正常”，只是全拒答。
- **怎么改的**：① `app/rag.py` 加 `_chunk_ids`：ID 改成 `{论文名}-{页码}-{chunk_start}-{页内序号}`，同一页里第几个片段就标几，同一个 `chunk_start` 也不会撞；同一份数据重复入库时 ID 不变，upsert 仍能按 ID 去重覆盖。② `add_chunks` 改成分批 upsert（每批 500 个），一批出问题不会把整库拖下水。③ 新增 `tests/test_ingest_ids.py`：合成用例复现单句片段的 `chunk_start` 重复，断言 ID 唯一；真实文献全量检查（26 篇 4220 个片段）断言 ID 唯一。
- **提效**：本地复现确认 85 个重复 ID（和用户报错的数字一致），修完后测试 10/10 通过（新测试 2 个 + 多轮测试 8 个），真实文献 4220 个片段 ID 全唯一。用户本地重跑入库 + 评测后填数字。教训：入库 ID 必须保证唯一，不能拿“位置”当 ID——位置会重复；批量写入要分批，别让一次校验失败清空整库；检索返回空时要能看出来，别静默拒答。补救：新增 `tests/test_ingest_roundtrip.py` 入库烟雾测试（假 embedding + 临时 Chroma，切分 → 入库 → 查库全流程），以后改切分、改 ID、改入库逻辑都要先过这个测试，不再等到用户跑评测才发现库是空的。

- **开始的效果**：第四轮 12/15，引用准确率 100%，应拒答 5/5，编造 0；没答出的 Q01/Q09/Q11 全是检索排名问题。

- **原因**：Anthropic 的 Contextual Retrieval 就是治这个的——入库前给每个片段加一段上下文再算 embedding。完整版是 LLM 给每块写一段话，4220 次调用又贵又慢；便宜版是不调 LLM，只贴现成的结构信息（论文标题 + 页码 + 章节）。
- **怎么改的**：① `app/ingest.py`：`chunk_pages` 给每个片段加 context 字段 "【文献：标题｜第 N 页｜章节】"；章节按页首附近（前 1500 字内）第一个标题启发式识别，没有就沿用上一页，第 1 页默认"标题与摘要"——这个口径是查出来的：Ge p.1 的引言标题在 2500 字后，用"页内最后一个标题"会把整页标成方法，用"页首附近第一个标题"才标对。② `app/rag.py`：`add_chunks` 把 context+正文一起入库算 embedding；`retrieve()` 和关键词检索都剥掉上下文行，回答员只看原文，引用不变。③ 新增 `tests/test_context.py`（6 个测试：标题识别、页首口径、上下文与正文分离、剥离回路、入库查库回路）。
- **提效**：本地 17/17 测试通过；BM25 探针 Q01 目标片段从第 7 名升到第 6 名（仍差 1 名没进前 5，BM25 这头基本到顶了）；向量那头的提升要等用户本地跑评测看数字。教训：章节标签是检索提示，不是精确标注——单页单标签在跨章节页面上一定有错，够用就行，别为标签完美再返工。

## 17. 评测拒答判定太脆：模型换个说法就漏判，第七轮 Q09 被算成“已回答”（2026-11-25）

- **开始的效果**：第七轮评测（关重排、留图注）终端显示已答 14、拒答 6，答出 14/15、引用准确率 92.9%，看着是最好的一轮。
- **遇到的问题**：逐题核对 results.json 发现 Q09 的答案实质是拒答——“根据现有文献片段无法回答……具体数值”，只给了回归系数 0.042，还特意说这不是年均变化率，1.8% 一个字都没提。脚本却算成“已回答”。回头用修复后的判定重算全部已存的 results.json：第二轮也被漏判 3 道（Q01、Q08、R03），第三轮漏判 1 道（Q08），都是拒答变体。
- **原因**：`eval/run_eval.py` 的拒答判定是固定开头匹配（`answer.startswith("根据现有文献无法回答")`），模型在“根据现有文献”和“无法回答”之间插词就对不上：第七轮 Q09 插了“片段”，第三轮 Q08 是“根据现有文献片段，**无法回答……”还带了加粗符号，第二轮 Q01 是“无法回答；……”用了分号、R03 是“无法回答具体‘快多少’”。判定只认一种写法，模型一换说法就漏。
- **怎么改的**：`eval/run_eval.py` 加 `is_refusal(answer)`：取回答的第一句（按 。！？；\n 切），第一句里出现“无法回答”就是拒答。只看第一句是因为已答题的后半句也可能出现“无法回答”（Q03 第五轮“峰后至 50 岁前的具体变化，根据现有文献片段无法回答”是部分拒答不是整题拒答），全句匹配会把这类答出的题错判成拒答。主流程改用 `is_refusal(answer)`，`REFUSAL` 的导入随之删掉（只在 agent 里用）。新增 `tests/test_eval_figure.py::test_is_refusal_first_sentence`（8 组用例：固定开头、片段变体、冒号、分号、加粗、正常回答、后半句部分拒答、空字符串）。只改评测的计分，不动 agent 的运行时行为。
- **提效**：全量测试 31/31 通过（新增 1 个）。重算结果：第二轮 7/15 → 5/15（和“实质仍 5 道”的判断对上了）、引用准确率 14.3% → 20%（1/5）、应拒答 4/5 → 5/5、编造 1 → 0；第三轮 11/15 → 10/15、引用准确率仍 100%（10/10），Q08 是拒答不是部分答对；第七轮 14/15 → 13/15、引用准确率 92.9% → 92.3%（12/13），和第五轮实质持平。第四、五、六轮没变。教训：评测的判定规则要按模型的实际输出写法来写，不能只认一种固定格式；每次改判定都要把历史 results.json 重算一遍，看哪些轮次的数字变了。
